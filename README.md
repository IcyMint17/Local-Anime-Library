# 本地番剧媒体库管理器

把你硬盘上按字幕组原始命名堆放的番剧文件，整理成一个像 Animeko 那样的可视化番剧库：自动扫描、自动识别番剧、拉取封面与剧集信息，并手动记录看到第几集。

只读扫描——**不会移动、重命名或删除你的任何文件**。

## 快速开始

1. 需要 Node.js **22.5 或更高版本**（`node --version` 查看）。不需要 `npm install`，本项目零第三方依赖。
2. 双击 `start.cmd`。
3. 浏览器会自动打开 `http://127.0.0.1:5178`，在「媒体库」页点「扫描媒体库」开始整理。

第一次扫描要访问 Bangumi 抓取元数据和封面，23 部番大约 1 分钟；之后有缓存，重复扫描只要几秒。

## 它是怎么工作的

```
扫描目录 → 解析文件名/文件夹名 → 去 Bangumi 搜索并打分 → 落地到本地 SQLite
```

1. **扫描**：递归遍历扫描目录，只挑视频文件（mkv/mp4/avi/…），自动跳过字体、字幕、扫描图、CD 音轨和 BD 菜单。
2. **解析**：从发布文件夹名与文件名里提取番剧标题、季数、集号，以及判断这是正片、特别篇还是剧场版。支持 `- 01`、`[01]`、`01v2`、`[12END]`、`S01E03`、`第3集`、`11.5` 半集、`NCOP/NCED/特典/小剧场` 等真实命名。
3. **识别**：用文件夹名（通常是中文）和文件名解析出的标题（通常是罗马音）分别去 Bangumi 搜索，再按名称相似度、季数、集数、媒介类型、搜索结果排名综合打分。只有最高分足够高、且明显领先第二名时才自动绑定，否则标记为「待确认」。

   一个文件夹里**只有一个文件、而且文件名里没有集号**时，直接按剧场版处理——`小林家的龙女仆 怕寂寞的龙` 这种既没有「剧场版」三个字、文件名里也没有 `Movie` 的情况，靠这条规则才能认出来。

   低置信度时会自动拉取候选项的详情，用 Bangumi 的**别名**再算一遍——这就是 `GIRLS BAND CRY` 能正确对上「少女乐队的呐喊」的原因。

4. **落地**：番剧、文件、剧集、观看记录都存进 `data/library.db`，封面缓存在 `data/covers/`。扫描过一次之后断网也能正常浏览。

## 观看记录

- 每集一个勾选框，精确到集。
- 整部番的 **未看 / 观看中 / 已看完** 由集进度自动推导，不会出现两边对不上的情况。
- 特别篇、NCOP/NCED、小剧场、剧场版单独成列，**不计入正片进度**。
- 提供「全部标记已看」「全部标记未看」一键操作。
- **双击任意一集**就会用系统默认播放器打开对应视频（也可以点悬停出现的「▶ 播放」按钮）。
- **收藏**：海报右上角或详情页的爱心，收藏的番剧会出现在「收藏」页，保存在本地数据库里。

## 界面

界面是暗色玻璃拟态（Dark Glassmorphism）风格，所有页面共用一条悬浮的液态玻璃 Dock，可以摆在窗口左侧、底部或右侧：

| Dock | 内容 |
| --- | --- |
| 首页 | 继续观看、我的番剧、时间线小卡片、最近添加（默认折叠） |
| 时间线 | 继续上次观看、追番日历、按天查看观看记录、未来一周更新 |
| 媒体库 | 左侧筛选栏 + 右侧海报墙（可切换列表） |
| 收藏 | 收藏的番剧，按类型筛选 |
| 设置 | 外观 / 媒体库 / 番剧识别 / 网络 / 高级 |

- **顶栏**：品牌图标、居中的搜索框、深色 / 亮色切换、设置快捷入口；桌面版右上角是窗口按钮。
- **继续观看**：只显示还有正片没看的最近番剧，点卡片进详情，点圆形播放按钮直接播下一集。
- **媒体库**：左侧上方是「全部 / 未看 / 观看中 / 已看完」，下方单独一张筛选卡放「TV 版 / 剧场版」和年份下拉框（选「全部年份」即可取消），右侧可以切换海报墙或列表，并按添加时间、评分、名称、进度排序。
- **收藏**：爱心状态存在 SQLite 里，重启后仍然保留；媒体库里不再重复放收藏筛选。
- **首页海报**：只保留标题和观看进度，评分、状态徽章都收进详情页，避免主页面堆太多元数据。
- **主题配色**：设置里有 6 套预设加一个取色器，只影响按钮、进度条、选中态等强调色。
- **液态玻璃**：设置里用分档滑动条调节所有玻璃面板的模糊强度（0–48 px），Dock 位置也可以即时切换。
- **深色 / 亮色**：点顶栏的太阳 / 月亮图标切换，亮色模式同样保持玻璃质感。

  深色 / 亮色、主题配色、Dock 位置和玻璃强度都存在 `config.json` 的 `ui` 里。桌面版每次启动都会用一个**新的随机端口**，换句话说页面每次都是一个新来源、localStorage 是空的——偏好放在服务端才能重启后照样生效。

- **自定义背景图**：设置里上传一张图片即可作为页面背景，并实时调节模糊程度和亮度；没有上传时只显示上传 / 清除按钮，不会拿番剧封面凑数。图片存在本地数据目录（`background.jpg`），不会上传到任何地方，「清除背景」随时还原。

应用图标是 `public/icon.jpg`，同时用作页面左上角的标志和浏览器标签页图标。

详情页是居中弹出的玻璃面板：左栏放封面、标题、评分、简介和来源路径，右栏是可独立滚动的剧集列表（正片 / 特别篇 / 剧场版 / 未收录 分标签）。所以哪怕一部番有五十多个文件，页面也不会被撑长，封面和信息始终留在屏幕上。窄窗口下自动改为上下堆叠。

剧集行默认只显示 `1080p · HEVC · 421 MB` 这类关键信息；点一下这行文件信息会弹出完整详情（容器、视频编码、音频、字幕、大小、路径和原始文件名），右上角的「打开文件夹」可以直接在文件管理器里定位番剧目录。

详情页右侧还会从 Bangumi 异步补充评分分布、收藏 / 在看 / 想看人数、角色与声优、制作人员、别名和标签；这些信息会缓存到本地数据库，第二次打开不再请求网络。

「打开文件夹」由运行服务的机器执行：浏览器版会在本机资源管理器里打开目录；如果页面是从另一台设备访问的，窗口只会出现在服务器那台机器上。

## 手动纠错

自动识别不是万能的。遇到下面这些情况，在详情页点「重新匹配…」即可：

- 搜不到，或者匹配到了相邻的一部（比如同名的第二季）。
- 文件名里的标题比文件夹名更好搜（字幕组资源常见：文件夹是中文名，文件名是英文或罗马音）。对话框里会把文件名里的标题列出来，点一下就直接拿去搜。

详情页同时会列出「Bangumi 上有、本地没有」的剧集，方便你知道还缺哪几集。

已知会被标成「待确认」的典型场景：文件夹名只说「某某剧场版」，真正的副标题只在文件名里（例如 `中二病也要谈恋爱剧场版` + `-Take On Me-`）。在候选列表里点正确的那一条即可。

### 集号对应关系

本地文件的集号经常和 Bangumi 对不上，程序会**自动推断**，不需要你算偏移量：

| 情况 | 本地集号 | Bangumi 集号 | 自动得出 |
| --- | --- | --- | --- |
| Re:Zero 第四季 丧失篇 | 67–76 | 67–77（Bangumi 的连续编号） | 一一对应 |
| 无职转生 第二季 | 0–24（含第 00 集） | 0–24 | 一一对应 |
| 无职转生 ～…～ 第2部分 | 12–24 | 12–23 + SP 24 | 一一对应，第 24 集是特别篇 |
| 孤独摇滚！ | 1–12 + 11.5 | 1–12 + SP 11.5 | 一一对应，11.5 是特别篇 |

推断规则是「让尽量多的本地集落在 Bangumi 剧集上」，平手时优先让两个序列从开头对齐。详情页左栏会显示当前对应关系和「N/M 集对得上」。

### 正片与特别篇以 Bangumi 为准

Bangumi 会把条目里的章节分成**正片**和**SP / OP / ED / 预告**。程序会把这些全部取回来，只要本地文件对上的是一条非正片章节，就自动归入「特别篇」、不计入正片进度——不需要靠文件名猜。

两个容易踩的坑已经处理掉了：

- **SP 用自己的一套编号**。「孤独摇滚！」的正片是 1–12，SP 也是 1、2、3、11.5。程序按「正片优先」配对，所以 `[01]` 是正片，`[11.5]` 才是特别篇。
- **Bangumi 的连续编号（sort）才是准的**。无职转生 第2部分、Re:Zero 第四季这类条目的集号不是从 1 开始，程序直接用 Bangumi 的编号，因此和本地文件名天然对齐。

个别文件夹会混用两种编号（例如 Re:Zero 第三季里既有 `01`–`14` 又有 `66END`）：程序先按偏移映射，只有当偏移落空时才会把原集号当成正确值。

如果推断得不对，在详情页点「重新匹配…」，对话框里就能改：勾「自动推断」由程序重算，取消勾选后直接填「本地第 ___ 集 = Bangumi 第 ___ 集」。手动指定的对应关系会锁定，重新扫描不会被覆盖。

## 配置

界面上点「设置」可以改，配置存在项目根目录的 `config.json`：

| 项 | 说明 |
| --- | --- |
| `scan.dirs` | 扫描目录，可以配多个 |
| `proxy` | `auto`（默认，自动探测）／留空（直连）／`http://127.0.0.1:7890` 这样写死 |
| `metadata.matchThreshold` | 自动匹配阈值，越高越保守 |
| `metadata.matchMargin` | 第一名必须领先第二名多少分才会自动绑定 |
| `metadata.accessToken` | 可选。填 Bangumi 个人令牌可以提高接口配额 |
| `appearance` | 背景图文件名、模糊度和亮度 |
| `ui` | 主题配色、深色 / 亮色、Dock 位置、玻璃强度 |

Bangumi 在国内通常可以直连。如果机器需要走代理，程序会按这个顺序自动找：环境变量 `HTTPS_PROXY` / `HTTP_PROXY` → Windows 系统代理设置 → 常见本地端口（7890 / 7891 / 7892 / 10809 / 1080 / 8080 …）。找到之后会实际连一次 Bangumi 验证可用性，结果缓存在 `config.json` 里。

写配置时是**在当前文件上合并改动**，不是用默认值重写整份，所以改某一项不会把别的设置（比如背景图）一起重置。


## 开发

```bash
node --test                      # 全部测试
node tools/inspect-library.mjs   # 看扫描/分组结果，不发网络请求
node tools/inspect-db.mjs        # 看本地数据库内容
node tools/evaluate-matching.mjs # 用真实库跑一遍识别准确率（会联网）
node tools/inspect-mapping.mjs   # 看某部番的本地集号↔Bangumi 集号对照
node tools/bench-library.mjs     # 对比 /api/library 的进度计算开销
```

扫描进度通过 `GET /api/scan/stream`（Server-Sent Events）推送给界面，空闲时另有 5 秒的心跳轮询兜底——这样即使一次暖缓存扫描只有两秒，界面也能看到它从开始到结束的全过程。

代码结构：

```
src/
  main.js             入口：配置、数据库、代理探测、启动服务
  config.js           配置读写与代理自动探测
  net/http.js         支持 CONNECT 代理隧道的 HTTP 客户端（重试 + 限流）
  db/                 SQLite 建表与全部读写
  scan/               遍历、文件名解析、分组、扫描流水线
  meta/               Bangumi 客户端、候选打分、封面缓存
  library/progress.js 观看状态推导
  api/routes.js       REST 接口
  server.js           静态文件 + JSON API 服务
public/               前端（原生 HTML/CSS/JS，无构建步骤）
test/                 node:test 测试，全部使用真实文件名
```

零第三方依赖是刻意的：不需要 `npm install`，离线可用；将来打包成桌面应用时体积小，也不会有原生模块编译问题。

## 桌面版（Electron）

浏览器版和桌面版共用同一套后端代码（`src/app.js` 的 `startLibraryApp()`），
桌面外壳只是换了个加载方式，没有第二份实现。

```
cd desktop
npm install          # 首次需要，从镜像下载 Electron 二进制
npm run make-icon    # 由 public/icon.jpg 生成 icon.ico
npm start            # 开发模式运行
npm run pack         # 打包到 desktop/dist/AnimeLibrary-win32-x64
```

打包脚本会先把 `src/`、`public/`、`config.json` 和外壳文件整理进 `staging/`，
再交给 electron-packager 打成 `app.asar`。外壳文件列表在 `desktop/stage.mjs`——
新增外壳模块时要一起加进去，脚本会检查 staging 里所有相对导入是否都能解析，
漏文件会在打包时报错而不是等用户启动失败。

| | 浏览器版 | 桌面版 |
| --- | --- | --- |
| 代码位置 | 项目目录 | `resources/app.asar`（只读） |
| 数据目录 | `<项目>/data` | `%APPDATA%\AnimeLibrary\library` |
| 设置文件 | `<项目>/config.json` | 同数据目录下 |
| 端口 | 5178（可在设置里改） | 每次启动由系统分配 |

桌面版的启动日志写在 `%APPDATA%\AnimeLibrary\startup.log`——窗口应用没有控制台，
启动失败时先看它。菜单「帮助 → 打开数据文件夹」可以直接定位库文件。

> 桌面版使用独立的数据目录，所以第一次启动会重新扫描一遍；这不影响命令行版的库。

### 窗口标题栏

桌面版是无边框窗口，顶栏本身就是标题栏：

- **拖动**顶栏空白处（品牌区、搜索框两侧）可以移动窗口，拖到屏幕边缘照样能贴边分屏；双击顶栏最大化 / 还原。
- 右上角三个按钮是最小化、最大化 / 还原、关闭，鼠标悬停在关闭上会变红。最大化后按钮图标会变成「向下还原」。
- 因为系统标题栏没有了，菜单栏也一并消失。**顶栏右侧的 ⋮ 按钮**会把原来的「文件 / 视图 / 帮助」菜单弹出来（清理缓存就在这里），快捷键（Ctrl+R 重新载入、F11 全屏、Ctrl+Shift+I 开发者工具）不受影响。
- 浏览器版不受影响：这些按钮只在外壳注入了 `desktop/preload.cjs` 的桥时才出现。

代价是失去了 Windows 原生标题栏的两样东西：悬停最大化按钮时的**贴靠布局（Snap Layouts）**浮层，以及 Alt+Space 系统菜单。贴边分屏、双击最大化仍然可用。

### 缓存与磁盘占用

`%APPDATA%\AnimeLibrary` 里有两类东西：

| 内容 | 例子 | 能不能删 |
| --- | --- | --- |
| **库本身** | `library\library.db`、`library\covers\`、`library\config.json`、`library\background.jpg` | 不能，这是你的番剧库 |
| **Chromium 缓存** | `Cache\`、`GPUCache\`、`ShaderCache\`、`DIPS\` … | 随时可删，会自动重建 |

缓存会失控是因为「重新匹配」对话框会加载 Bangumi 返回的**每一条候选的封面原图**——一次搜索 12 张、每张约 900 KB，而 Chromium 全都会写进磁盘缓存。作者这边用了一阵子就攒到 **381 MB / 986 个文件**，整个目录 409 MB。

现在做了两件事：

- 启动时先清空这些缓存目录，且不再往磁盘缓存写（应用需要的封面本来就存在 `library\covers\` 里，并且是从本机 127.0.0.1 取的）。实测同一个目录从 409 MB 降到 **19.5 MB**（其中 19.3 MB 是库本身），正常使用不会再涨回去。
- 候选列表改用缩略图而不是原图，一次搜索的流量从约 11 MB 降到几百 KB。

想手动清一次：

```
桌面版设置：设置 → 高级 → 清理缓存   # 显示当前占用，确认后清理并刷新读数
桌面版菜单：帮助 → 清理缓存…         # 应用开着也能用，会告诉你释放了多少
node desktop/clean-cache.mjs         # 命令行，需要先退出应用；可加参数指定其它配置目录
```

这些入口只会删上面那张表里的缓存，**不会碰** `library\`、设置、封面和背景图。

### 任务管理器里那个 0.1 MB/s 的「磁盘」是什么

它不是你硬盘上的读写。实测：窗口开着不动 30 秒，Electron 的 profile 目录
`%APPDATA%\AnimeLibrary` 在文件系统监视下**零事件、零字节增长**，同一时间
进程 I/O 计数器却在动。

原因是 Windows 的任务管理器「磁盘」一列读的是进程 I/O 字节计数，其中包括
**命名管道**的流量；而 Chromium 的渲染进程和 GPU/浏览器进程之间一直用管道
传 IPC 消息。所以计数器在走，磁盘并没有被碰。

几个对照实验（`desktop/` 下的本地探针）：

| 场景 | 结果 |
| --- | --- |
| 同样的 Electron 加载空白页 | 所有进程都是 0 B/s |
| 加载本应用页面 | 渲染进程写约 6 KB/s，GPU 进程读约 6 KB/s |
| 切换背景图 / 主题的瞬间 | 一次重绘尖峰，约 1 秒后回落到稳态 |
| 关闭硬件加速 | 没有改善 |
| 页面静止 30 秒的 profile 目录 | 文件系统事件 0 次，字节数不变 |

计数器的绝对值会随测量方式变化（同一状态下不同探针能测出 6 KB/s 和
120 KB/s 两种结果），所以结论不建立在这些数字上，而是建立在上面最后一行：
**没有任何文件被写入**。

应用本身没有任何周期性写盘——只有扫描、下载封面、改设置时才写文件，所以
日志和缓存都不是持续读写的来源。上面的稳定性开关（关闭组件更新、域可靠性
等后台服务）能减少真实的后台活动，但不会改变任务管理器里那个数字。
